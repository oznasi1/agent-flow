E2E Lane Expansion — Deck lifecycle, sidebar, Marketplace & Notepad, PR review, and the parked hosts

Take the real-host lane from eleven journeys over the take/seed core to the app's remaining user-facing surfaces — and make a green run mean something by turning one-time sabotage discipline into a repeatable gate.

Speed was explicitly not a goal, and is therefore treated as a constraint to respect rather than an objective to chase: the design spends boots where they buy coverage and saves them where grouping is free, but it does not restructure the lane for latency. §8 names the escape hatch if the required check ever gets painful.

2 · The lane today

Eleven journeys in test-e2e/, workers: 1, fullyParallel: false, one Electron VS Code 1.96.2 per test(), retries: 1 in CI. The lane is a required check on every PR (.github/workflows/e2e.yml) and generates the Layer C verify-feature report on every run, pass or fail.

The five seams that make it deterministic

Everything below reuses these; nothing new is invented where one already fits.

  • The fixture connector — agentFlow.taskSource: "fixture" and AGENT_FLOW_FIXTURE_DIR, both required, so a shipped install can never resolve it. Tasks read from tasks.json; every write appends to writes.jsonl.
  • A sandboxed HOME — ~/.agentflow, run records and flows all land in a temp root that is disposed per test.
  • PATH shims — the sandbox owns the child's PATH and puts its own bin/ first. open exits 1 (forcing the in-process vscode.openFolder fallback rather than launching the developer's real editor); claude prints a marker and holds stdin.
  • Forge shims — gh/glab match the first two argv words (tr-mangled per character) against canned JSON, log every call to calls.jsonl, and log unmatched argv to unknown.jsonl while returning [].
  • Host flags that stop escapes — --force-disable-user-env (or macOS re-resolves PATH from the login shell and drops the shims), --use-inmemory-secretstorage (or a sandboxed HOME throws a modal "Keychain Not Found"), and deleting ELECTRON_RUN_AS_NODE from the child env.

3 · Scope

InOut, and why
Deck lifecycle — retire, forget, track, clear-stale, Address PR Orchestrator — the largest uncovered subsystem, but it needs two windows driven at once against a cross-window lock and a 6 s evaluation pass. It deserves its own spec, not a corner of this one.
Sidebar actions — detail, Explore, labels, reorder, sprint, component; child trees at Take time Setup wizard & Doctor — not selected. Doctor's fixture probe deliberately returns {} so it renders "skip"; a journey would assert almost nothing without product change.
Marketplace and Notepad — two webview bundles with zero real-host coverage Real Jira connector — rejected. It needs secrets in CI and breaks the lane's offline property, which is the thing that makes it trustworthy.
PR review — the review rail, single launch and batch Parallel workers — rejected. The runner is 2–4 cores, Electron is heavy, and a flaky required check is worse than a slow one.
Copilot Chat panel, Cursor provider, Cursor-as-host (spike) @core/@extended lane split — held as an escape hatch (§8), not built.

4 · Harness changes

Four additions under test-e2e/_helpers/. Existing journeys are not rewritten — they keep calling launchHost per test.

4.1 sharedHost.ts — one boot per file, for read-only groups

A describeWithHost(title, settings, fn) wrapper that boots one Electron in beforeAll, disposes in afterAll, and forces test.describe.configure({ mode: "serial" }) so a failure skips the rest of the group instead of running the remainder against a half-mutated host.

The cost, stated plainly
Tests inside a group share state and are order-dependent. That is acceptable only for surfaces whose actions are local (Notepad's globalState, the Marketplace's reads) or additive (writes.jsonl is append-only, so each test asserts its own appended line by op and key rather than the file's whole contents). Any journey that opens a window, creates a worktree, or writes a run record stays one-boot-one-test.

4.2 po/ — page objects

po/pool.ts, po/deck.ts, po/marketplace.ts: intent-named methods (selectRepo("rocket"), openCardMenu("E2E-1"), retire(key)) wrapping the frame locators. Today nine files select on raw CSS classes — .card, .batch-bar, .repo-select-trigger — so one class rename is a nine-file repair. No data-testid attributes are added to src/: the page objects centralise the existing selectors, they do not change the product to suit the test.

4.3 Shim extensions

  • ghReviewRequestsAnswer() in forgeShim.ts — the review rail shells gh api graphql with a search(type:ISSUE) query (src/engine/review/search.ts). The signature api graphql mangles to api_graphql, so it slots into the existing first-two-words scheme with no shim rewrite. The builder emits data.search.issueCount and nodes, because parse returns null for anything that is not that shape.
  • A cursor-agent shim — modelled exactly on the claude one (print a marker, exec cat to hold stdin) so the Cursor provider's terminal seed lands in a "running" TUI and the developer's real CLI can never start a session from a test.
  • expectNoUnknownForgeCalls(sb) — see §6.2.

4.4 copilotChat.ts

Pins GitHub.copilot-chat into the sandbox's extensionsDir using the pattern claudeCode.ts already proves: gallery vspackage download, gunzip when the magic bytes say so, install through VS Code's own CLI into a staging dir, cache under .vscode-test/ keyed on version + platform. The CI cache key in e2e.yml gains this file so the pin and the cache stay in step.

Named risk
Copilot Chat may refuse to register workbench.action.chat.open until signed in. If so, the journey inverts into a pin: assert that the command is absent and the clipboard fallback fires — which is what copilot-fallback.e2e.ts already proves, so the honest outcome is to delete the new journey and record the finding rather than ship a test that asserts nothing. This is a go/no-go inside the task, like §7.

5 · The fixture connector gains three capabilities

This is the design's only src/ change, and it is deliberate.

Today the fixture advertises supportedFilters: ["mine","all"], sizes: false and labels.add — nothing else. The capability record is doing its job: with no sprints, components or children member, the sidebar correctly hides those lenses, so addToMySprint, removeFromSprint, setComponent and child expansion are not merely untested — they are unreachable from any E2E host.

The fix is to have the fixture claim all three, each recording to writes.jsonl the way labels.add and moveTo already do:

sprints:    { activeId, add(sprintId, key), remove(key) }
components: { list, update(key, { add, remove }) }
children:   { of(key) }   // one level down; the caller recurses (engine/taskTree.ts)

Two fixture tasks gain a parent/child relation and an inOpenSprint variation so the lens has something to show.

Why this does not violate "never break existing users"
makeFixtureConnector is reachable only when agentFlow.taskSource: "fixture" and AGENT_FLOW_FIXTURE_DIR are both set; CONNECTOR_IDS is untouched and a dedicated unit test already pins that gate. Nothing in the released surface frozen by test/unit/compat.test.ts moves. The capabilities added are ones a real Jira source genuinely has, so the fixture becomes more faithful, not a fabrication shaped to suit a test.

6.1 Shared-host groups — three boots, ~14 assertions

FileTestsAsserted from

Why the drag test is the single highest-value item in this group
An element with draggable cannot be text-selected in Blink, and preventDefault on dragstart does not give the gesture back. jsdom cannot see either fact — which is exactly how the known Tasks-tab selection bug survives a full green unit suite. Playwright driving a real Electron is the only harness in this repo that can observe it. The Notepad journey asserts both the reorder and that a note's text remains selectable.

Clipboard note. mkt:copy calls vscode.env.clipboard.writeText, which reaches the real system clipboard — the sandbox does not contain it, and copilot-fallback.e2e.ts already has this property today. The journey therefore asserts the "Copied to clipboard." toast in the workbench notification DOM rather than reading the clipboard back: reading it is unreliable headlessly and would make the assertion depend on state the test cannot own.

6.2 Per-test journeys — seven boots

review-launch.e2e.ts — the flow the user named. gh api graphql is shimmed to return one review request on rocket#41; the Deck's review rail renders it; "Review with Claude Code" launches. Assertions: a real git worktree named review-rocket-41 exists and is git-registered (the key comes from reviewRunKey, review-<repo-slug>-<number>), the brief is inside it, the plan handshake carries the review-rendered template with {repo}, {number} and {author} substituted, and the run record exists under ~/.agentflow/runs/. A second test() in the same file drives deck:reviewBatch across two PRs and asserts two worktrees and two run records.

deck-lifecycle.e2e.ts — retire a run and watch the card leave the board; forget an untracked run; track one back; clear stale. Assertions come from ~/.agentflow/runs/ on disk plus the Deck DOM, so a UI-only change that never touches the record fails.

address-pr.e2e.ts — Address PR from the sidebar (addressPr) and from the Deck (deck:addressPr), both against the shimmed gh. Asserts the seeded prompt names the PR and that the session opens against the PR's branch.

cursor-provider.e2e.ts — agentFlow.agentProvider: "cursor" with the terminal surface. Asserts the prompt reaches the cursor-agent shim's xterm DOM unsubmitted. This path shipped in 0.33.0 without ever running in an editor; the journey is the first execution of it in CI.

copilot-panel.e2e.ts — real pinned Copilot Chat, subject to §4.4's go/no-go. copilot-fallback.e2e.ts stays as the no-extension case; the two together pin both sides of the branch.

child-tree-take.e2e.ts — agentFlow.childWorktrees is on and the fixture now claims children, so taking E2E-1 finds E2E-1-a one level down and offers the tree. Asserts a git-registered worktree per child. Corrected during planning: children surface at Take time behind probeTree (tasksView.ts), not as a sidebar tree expansion — it opens windows and creates worktrees, so it cannot share a host and belongs here rather than in §6.1.

cursor-host.e2e.ts — created only if §8's spike says go.

7 · Hardening — making green mean something

7.1 Sabotage becomes a repeatable gate

Every journey shipped so far carried a sabotage check: break the product, watch the journey fail, revert. But it was performed once, by hand, during development — which is precisely how a journey that has since gone vacuous stays green forever. This design makes it standing infrastructure:

1
Apply
test-e2e/sabotage/<journey>.patch, one per journey
→
2
Rebuild
E2E asserts the bundle, so a bare re-run would test stale dist/
→
3
Run that one journey
and require a failure
→
4
Revert
git diff --exit-code as proof the tree is clean

scripts/sabotage.mjs [journey] drives it; a weekly CI job runs the full set. It is deliberately not a per-PR gate: it rebuilds and re-runs per patch, which is far too slow for the required check, and its failure mode ("a test stopped being able to fail") is a standing-health question, not a merge-blocking one.

The scar this addresses
On a prior plan, six plan-authored tests turned out to be vacuous or impossible while the implementers' code was correct — the tests were the defect source. A green suite that cannot fail is worse than no suite, because it is believed. Note also that a sabotage check only means anything against committed work: the git checkout that restores the mutant also reverts any uncommitted fix.

7.2 Unfaked shell calls fail loudly

The forge shim's unknown-argv handling is self-discovering by design: log to unknown.jsonl, return [], exit 0 — so the first run against real code reports what else must be faked instead of crashing cryptically. That is right during development and wrong forever after: once a journey is green, a product change that starts shelling a new subcommand silently receives an empty answer and the journey keeps passing. expectNoUnknownForgeCalls(sb) in each forge journey's teardown asserts unknown.jsonl is empty or absent.

7.3 Flake stops hiding

CI keeps retries: 1 — dropping it would make a required check hostile — but scripts/verify-report.mjs learns to read each result's retry count and mark "passed on retry" in the markdown summary and the sticky PR comment. Today a journey that only passes the second time is indistinguishable in the report from one that passes cleanly, which is how an intermittently broken journey becomes permanent background noise.

8 · The Cursor-as-host spike — timeboxed, gates its own tasks

Measured on 2026-08-22: Playwright's _electron.launch against Cursor with --extensionDevelopmentPath and a fresh user-data never completes the launch handshake — the driver's inspector pipe does not answer, and it times out at five minutes. CDP was never tried.

The probe: launch Cursor with --remote-debugging-port=<n> as a plain child process, attach with chromium.connectOverCDP, locate the workbench target among the CDP pages, and assert .activitybar. Timebox: one session.

OutcomeConsequence
GolaunchCursorHost() joins host.ts beside launchHost, and one journey (smoke + take) runs on Cursor. Not the whole suite — the point is to prove the host boots and the extension activates, not to double the lane.
No-goA documented negative result in the plan's ledger, naming what was tried and how it failed. The Cursor lane stays manual. No other task depends on this either way — the Cursor provider journey (§6.2) runs on the VS Code host and is unaffected.

The spike runs first, before any plan task is written against it, so a no-go costs one session rather than a restructured plan.

9 · Runtime and CI

Boot count is the honest cost metric: each boot downloads nothing (the VS Code build is cached on the key that hashes host.ts and claudeCode.ts) but each pays full Electron start-up.

CI changes: the cache key in e2e.yml gains copilotChat.ts; a new weekly sabotage.yml job runs §7.1. The required check keeps its current shape — same job, same sticky comment, same artifacts.

Escape hatch, not built now
If the required check crosses roughly eight minutes, tag journeys @core / @extended and run only @core on PRs with the full set on merge-to-main. It is named here so the option is designed rather than improvised, and deliberately deferred because it lets a break reach main.

10 · Definition of done

  • npm run typecheck clean · npm test passes unmodified · npm run build succeeds · npm run test:cov thresholds hold · npm run test:ct passes · npm run test:e2e passes (11 existing + new).
  • The one src/ change is the fixture connector's three capabilities (§5), covered by unit tests that also re-pin the double gate.
  • Every new journey ships with its sabotage patch in test-e2e/sabotage/, and scripts/sabotage.mjs passes over the full set at least once.
  • No new dependencies. Pins move only deliberately: VS Code 1.96.2, Claude Code 2.1.238, plus the new Copilot Chat pin.
  • Lockfile hygiene: grep -c codeartifact package-lock.json → 0.
  • Both required checks green on the PR; merged via the REST path.
  • A CHANGELOG.md entry only if user-facing behaviour changes — expected to be none, since the fixture connector is unreachable in shipped installs.

12 · Findings from implementation

Two real product defects surfaced while building the Notepad journey (Task 5). Both are recorded here — not just in the throwaway execution ledger under .superpowers/sdd/..., which is deleted once this work lands — so a maintainer diffing the spec against the code later can still find them.

Finding A — post-drag text selection is broken (pinned by a test)

After a Notepad row is dragged to a new position, its body text can no longer be selected with the mouse. Deterministic — reproduced three times in a row, not a flake. In Blink, an element carrying the draggable attribute cannot be text-selected by mouse, and calling preventDefault() on dragstart does not hand the gesture back to selection — Blink forks "drag" from "select" at mousedown, before dragstart even fires, and does not revisit that fork afterward.

src/webview/Notepad.tsx:504-511 shows the author already anticipated exactly this trap and built an armed / draggable={armed} state machine meant to un-arm a row once its drag completes — but the reset on onDragEnd at Notepad.tsx:626 (() => { setArmed(false); dnd.onEnd(); }) does not fully hand the gesture back to selection for the row that was just dragged.

Pinned by test.fail() in test-e2e/notepad.e2e.ts ("dragging a note leaves its body unselectable afterwards (pinned defect)"). When this is fixed: delete the test.fail() line — not the test itself — which is what turns the test from "expected to fail" back into an ordinary passing regression check.

Finding B — Notepad globalState data-loss race (previously unknown, NOT fixed)

Two Notepad writes issued roughly 100–300ms apart can race: the second write's own read of agentFlow.notepad / agentFlow.notepadSections comes back as if the first write had never happened, and the second write clobbers it. Concretely observed as renameSection DELETING the section it was asked to rename — notepad:addSection persists and reads back correctly, but the very next message, notepad:renameSection, sent moments later, reads this.sections() back as [] with nothing else logged in between, so its own .map() over nothing writes [] right back and deletes the section.

Isolated by bisection with temporary instrumentation (a this.log() added to tasksView.ts, since reverted). A ~500ms pause between writes reproduces ordinary human pacing and eliminated the race 100% of the time in testing.

The E2E journey (test-e2e/notepad.e2e.ts) paces its own writes around this with a documented settle() helper — a workaround for the journey, not a fix for the product. This defect is not fixed. It is user-facing data loss in a persistence path: any two Notepad actions issued close enough together (add-then-add, add-then-rename, and likely others on the same write path) can silently discard state the user just entered.
