A fully-automated verify & release cycle

No manual gate. Every feature is proven end-to-end in a real editor host — driven, screenshotted, asserted, and reported — before it ships.

The goal in one line
Zero manual steps before a feature ships. No smoke checklist for the bits that cross into the OS and the Claude Code extension — instead, host-driven E2E is the core layer, and a screenshot-backed "verify feature" report (the pattern used at work) posts to the PR and gates the release.

1 · TL;DR

Drive a real VS Code Electron host with Playwright, running the actual extension against a fixture task connector (a JSON-backed TaskConnector, env-gated in the registry — no HTTP server, no network) and temp git repos. For each critical feature the run: takes the action, lets a real window open and the Claude panel seed, captures labelled screenshots at each step, asserts on real DOM + filesystem + the fixture's recorded writes, and emits a verify-feature report. A fast Playwright Component Test layer covers webview interaction (incl. the drag-and-drop jsdom can't reach). Both run in CI and block the release — no human in the loop.

2 · The goal

  • No manual testing, ever, before a feature ships. The release-on-merge flow gets an automated proof step, not a checklist.
  • Prove the feature in a real host — a real window opens, the real Claude Code panel receives its seed — not a mock's approximation.
  • Screenshots + a report as first-class output: an auto-generated "verify feature" artifact, deliverable to Slack / an internal endpoint / CI, mirroring the MCP flow you already use.
  • Deterministic enough to gate on — the whole thing is only worth it if it's green when the product is good and red when it isn't.

5a · Layer A — webview component tests

The quick inner loop. @playwright/experimental-ct-react mounts each real component in Chromium; a support file fakes window.acquireVsCodeApi (recording postMessage into window.__posted), mirroring today's jsdom vi.mock. Keep pure rendering in the existing vitest suite; CT covers interaction + measured layout only.

Priority targets — the jsdom blind spot. jsdom returns all-zeros from getBoundingClientRect(), so every feature whose logic depends on measured layout is untestable today. Of the 17 webview components, three measure layout and three implement drag:

#ComponentWhy CT is the only way
1App.tsx :804sprint drag-and-drop reorder — drop target computed from the measured rect
2Notepad.tsx :587note drag reorder — same measured-rect pattern
3OrchestratorDrawer.tsx :455, :622, :1385graph layout measured in four places — the most layout-dependent surface in the app
4DeckApp.tsxthird drag surface; in-flight row actions
5App core interactionsfilter tabs, size lens, fuzzy search, pick→confirm
6MarketplaceApp / PluginPicker / ReviewStripfilters, selection, review actions
This grew since the first draft
Drafted against v0.1.55, this was one untested drag surface. On v0.21.1 it is three layout-measuring components and three drag surfaces — Notepad and OrchestratorDrawer both landed in between. The case for Layer A got stronger, not weaker, and it will keep growing at this repo's release cadence.

5b · Layer B — real-host end-to-end (the heart of this plan)

How the host is driven. Use @vscode/test-electron only to download a pinned VS Code build; then playwright._electron.launch({ executablePath, args:["--extensionDevelopmentPath=…","--user-data-dir=…","--disable-workspace-trust"] }) to drive it. Playwright gets the workbench window, and can switch into webview iframes to click the real task pool. Screenshots, video, and trace come for free.

What each E2E proves (a real window genuinely opens — seeding rides on vscode.openFolder, workspace.ts:256):

#Feature journeyAutomated assertions
1Take a task — pick from pool → confirm → opena folder/workspace window opens; .pick-task/TASK.md written with the right brief; .code-workspace generated; correct repos resolved
2Claude panel seeds in the opened windowthe plan-handshake file is written; the Claude Code command fires; the panel shows the seeded prompt (DOM/text assertion + screenshot) — seeded, not run
3Status write-back from a cardthe fixture connector records the transition and the claude-code provenance label (writes land in a JSONL the test reads)
4Worktree modea real git worktree + branch is created off the temp repo
5Sign-in / sign-outtoken round-trips through SecretStorage (the one journey that keeps a Jira-specific seam); the pool renders the fixture's tasks
The boundary I won't fake
The gate proves the panel is seeded with the correct prompt — the extension's actual responsibility. It does not press Enter to run the agent: that is Claude Code's job, hits the Anthropic API, and would make CI slow, costly, and nondeterministic. "Seeded correctly" is the honest, sufficient contract — and it still needs no human.

5c · Layer C — the verify-feature report

Playwright already captures a screenshot/video/trace per step. Layer C curates them into the artifact you're used to: for each feature, an ordered strip of labelled screenshots ("1 · pool loaded", "2 · task picked", "3 · window opened", "4 · panel seeded"), a pass/fail verdict, and the run's metadata. Options, in priority order:

  • baseline Playwright's built-in HTML report + trace viewer (zero extra code) as the CI artifact.
  • the "verify feature" analog a thin generator that lays the labelled screenshots into a single self-contained HTML report per feature — matching that same flow.
  • out of scope No pixel-diff visual regression. No toHaveScreenshot(), no committed baselines, no baseline-maintenance tax. Screenshots are evidence attached to the PR, read by a human when they want to look — they never fail a build on their own. Correctness is proven by the DOM / filesystem / recorded-write assertions.
  • delivery the PR itself — see §5d. Slack / an internal endpoint remain optional extras.

5d · Delivering the report on the GitHub PR DECIDED

The report lands where the work is reviewed. Three mechanisms, used together:

MechanismWhat it givesCost

$GITHUB_STEP_SUMMARY		full markdown report on the Actions run page, linked from the PR's checks. Renders images from the Pages URL.trivial

(publish HTML report)		the real screenshot-strip report + Playwright trace viewer, at a stable URL the PR comment deep-links into.free — public repo
The one real constraint: screenshots must be hosted
GitHub sanitizes markdown in comments — data: URIs are stripped, so base64-inlined screenshots will not render in a PR comment. Images need a real URL. That's why GitHub Pages (free on this public repo) is in the mix: the run publishes the HTML report + PNGs there, and the sticky comment links/embeds from that URL. Fallback if Pages is undesirable: upload the report as a workflow artifact (downloadable zip) and keep the comment text-only with a link — less pretty, zero hosting.
Model-B wrinkle — worth deciding now
Under §8, Layer B runs at merge-to-main / pre-release, not on every PR — so by default a normal PR has only the CT results to report. To get a full verify report on the PR, add an on-demand trigger: apply an e2e label (or workflow_dispatch) and the full lane runs against that PR and posts its report. Best of both: PRs stay fast, and any PR can ask for the real-host proof on demand.

6 · Testability seams (the honest cost)

Decision (2026-08-21): fixture connector, not a fake Jira
A fake Jira asserts our model of Jira, not Jira — it can never catch Jira changing, so its marginal value over a fixture is small while its cost (a server process, ports, lifecycle, all inside the flakiest tier) is real. And it aims at the wrong layer: what E2E must prove is the host boundary, and the Jira HTTP client has zero VS Code API surface — it stays covered by unit/contract tests. TaskConnector is already the seam the pluggable-connectors work bought us.

A real, fresh host has empty settings and empty SecretStorage. With the fixture connector, the seam list shrinks to:

  • Fixture task connector — a JSON-backed TaskConnector (src/tasks/fixture/), registered in the connector registry only when an env flag names its fixture directory. Unset (every real user) → the registry is byte-identical to today: ships inert. It reads tasks from tasks.json and records every write (moveTo, labels) to writes.jsonl, which is what journey 3 asserts on — a request-recorder without a server.
  • Settings, not seams — every mid-take prompt is already answerable from settings: taskMode (a configured mode id skips the prompt-mode pick), openIn: "new-window", worktree: "never"|"always", remoteControl: "off". The repo-confirm QuickPick stays and is driven — it is real take UX, and the workbench quick-input is ordinary DOM.
  • Deterministic "opened-by-take" handshake — the seed handshake already uses a plan file with a 15-min TTL (workspace.ts, PLAN_TTL_MS); the test controls timing, no product change needed. The launcher overrides HOME for the child host so ~/.agentflow/plans lands in the sandbox, never in the developer's real home.
  • Test sign-in (journey 5 only) — sign-in/out genuinely exercises SecretStorage against the Jira connector, so that one journey keeps an env-gated seam (agentFlow.__test.signIn). Not needed for journeys 1–4.

What this deliberately gives up: nothing end-to-end exercises real Jira request/response shaping. That belongs to a contract test in the unit suite against a recorded real response — not to an editor-host lane.

Everything else the extension already does through real VS Code APIs, so the E2E exercises production code paths, not test shims.

7 · Host & platform constraints (read before committing)

  • reliable gate Stock VS Code is the target the release blocks on — it downloads reproducibly and Playwright-drives cleanly.
  • best-effort Cursor as host: your own hard-won note stands — the Cursor CLI silently drops --extensionDevelopmentPath. Playwright launches the binary directly (bypassing the CLI), so Cursor may work, but it's unproven. Treat a Cursor lane as a nice-to-have that never blocks a release until it's shown stable.
  • CI display Linux runners need xvfb to launch the Electron host headlessly; browsers/binaries are cached.
  • dependency The host must have anthropic.claude-code installed to verify seeding. CI installs a pinned build into the test host's extensions dir. If Claude Code is absent, the extension's documented fallback (write the brief, skip the panel) is what the E2E asserts instead — a valid path to cover too.
  • never in CI The agent is not run — no Anthropic API calls from the gate (see §5b boundary).

8 · Where it runs — the tiered gate DECIDED

Both CI and local, each doing the job it's good at. Extends the existing ci.yml (today: typecheck → vitest → build):

LaneRunsContainsBlocks
Fast (CI)every PR + pushtypecheck · vitest · build · Layer A (CT)merge — every PR
Full (CI)merge-to-main / pre-release, under xvfbLayer B (host E2E) + Layer C reportthe release
Localon demand — npm run test:e2ethe same Layer B specs, headed & debuggablenothing — authoring & the macOS-path check
macOS (CI)optional, nightlyLayer B on a macOS runner (covers open -a-class paths)advisory

Rationale: the fast lane keeps PR feedback in minutes; the full lane puts the expensive, real-host proof exactly at the moment it matters — the release — so no feature ships without an automated real-editor proof, and the manual checklist is retired. Release-on-merge stays as-is, now standing on that proof.

Cost — dollars, time, maintenance

DimensionReality for this repo
Dollars$0 — public repo → free unlimited Linux runner minutes. The only non-free path is macOS runners (~10×), which is why the macOS lane is optional/nightly, never per-PR.
Time — fast lane~5–8 min (typecheck + vitest + build + CT). The unit suite alone is now ~2.5 min with coverage at 3,769 tests — it grows with the repo, so watch this number.
Time — full lane~5–12 min for ~5 journeys. VS Code + Playwright binaries cached, so the download is seconds after the first run. Only at merge/pre-release.
MaintenanceThe real cost: human time triaging Layer B flakes. Budget it as ongoing, not one-time.

Reliability — by layer, because they differ sharply

  • high Layer A (CT, headless Chromium): standard Playwright, flake ≈ zero. No concern.
  • the flaky tier Layer B (real VS Code under xvfb): CI-stable with discipline — deterministic fakes (no real network), Playwright auto-waiting (never fixed sleeps), --no-sandbox/--disable-gpu + dismissing first-run UI (workspace-trust, telemetry, welcome), pinned VS Code and Claude Code builds, bounded retries with trace-on-failure, and a quarantine lane so one bad spec can't wedge the pipeline. Expect some early flake, driven to near-zero with hardening.
Honest limitation — macOS-only paths
A Linux gate proves all cross-platform logic but won't exercise the extension's macOS-only window handling (e.g. the open -a note in workspace.ts). Covered by the local run on your Mac and the optional nightly macOS lane — not by the per-release Linux gate.

WorkRough effort

The trade-off of "no manual step," stated plainly
Full UI automation is inherently the flakiest test tier — real windows, timing, focus. Making it a hard release gate means a flake can block a good release. This is the price of retiring manual testing, and it's payable, but only with discipline: deterministic fakes (no real network), Playwright auto-waiting (no fixed sleeps), bounded retries with trace-on-failure, and a quarantine lane for a newly-flaky test so one bad spec never wedges the pipeline. Budget ongoing maintenance, not just build cost.

Other risks

  • experimental Playwright CT + _electron-driving-VS Code are community-proven but not first-party VS Code testing → pin versions; keep the launcher thin and swappable for ExTester if it regresses.
  • webview iframes driving the extension's webview from the host means iframe-switching; encapsulate in one page-object helper.
  • Claude Code coupling a Claude Code UI change could break the seed assertion → assert on the seeded text we control, screenshot the rest, and pin the Claude Code build in CI.

11 · Definition of done

  • ✓ A real VS Code host launches in CI and drives the extension against the fixture connector + temp repos — no real network.
  • ✓ The core journeys (take task → window opens → panel seeds; status write-back + label) pass with assertions and screenshots.
  • ✓ A verify-feature report is generated every run and posted on the GitHub PR — sticky comment + job summary, with screenshots attached via the Pages-hosted report.
  • ✓ Drag-and-drop reorder is covered in real Chromium (Layer A).
  • ✓ The gate blocks the release on failure; no manual checklist remains.
  • ✓ A quarantine path exists so a single flake can't wedge the pipeline.
