# Reach stats

This is maintainer tooling, not a shipped feature — nothing in `scripts/reach/`
runs inside the extension, ships in the `.vsix`, or is reachable from a
webview. It exists because GitHub's traffic API only retains 14 days of daily
views and clones: whatever isn't recorded before that window closes is gone
forever, no exceptions. This doc is meant to be true, not encouraging.

## Before the first run: bootstrap the data branch

`.github/workflows/reach.yml` checks out an orphan `reach-data` branch to
read and write the store. **That branch does not exist on the remote until
someone creates it once.** Until it does, every scheduled or dispatched run
fails at the "Check out the data branch" step and collects nothing — silently,
since a failed `reach` workflow run does not block anything and nobody is
watching it by default. If the cron looks dead, check this first.

**The repository owner must run this** — it pushes directly to
`oznasi1/agent-flow`, so the account running it needs write access to that
repo. Use a push refspec so the shared root checkout is never switched:

```bash
cd "$(mktemp -d)"
git clone --depth 1 https://github.com/oznasi1/agent-flow.git bootstrap
cd bootstrap
git checkout --orphan reach-data
git rm -rf . >/dev/null
printf '# reach-data\n\nCollected reach statistics. Generated by .github/workflows/reach.yml on main.\nDo not merge this branch into main — it shares no history with it.\n' > README.md
git add README.md
git commit -m "chore(reach): bootstrap the reach-data store"
git push origin reach-data
```

After this runs once, the workflow's checkout step succeeds and the first
scheduled or `workflow_dispatch` run starts populating the store normally.
This is a one-time setup step, not something that needs repeating after the
branch exists.

## What is collected, and from where

| Source | Endpoint | Stored as |
| --- | --- | --- |
| Repo views | `GET /repos/oznasi1/agent-flow/traffic/views` | `traffic/views.json`, merged daily map |
| Repo clones | `GET /repos/oznasi1/agent-flow/traffic/clones` | `traffic/clones.json`, merged daily map |
| Referrers | `GET /repos/oznasi1/agent-flow/traffic/popular/referrers` | `snapshots/referrers/<date>.json`, one file per run |
| Paths | `GET /repos/oznasi1/agent-flow/traffic/popular/paths` | `snapshots/paths/<date>.json`, one file per run |
| Stars | `GET /repos/oznasi1/agent-flow/stargazers` (paginated, full history) | `stars.json`, sorted `starred_at` list |
| Open VSX downloads | `open-vsx.org/api/oznasi1/oznasi1-agent-flow` | one field per line in `marketplace.jsonl` |
| VS Marketplace downloads | `marketplace.visualstudio.com` extension query API | one field per line in `marketplace.jsonl` |

Referrers and paths are GitHub's top-10 rankings, not totals — two snapshots
don't compose into a sum, so each run keeps its own dated file instead of
merging into one aggregate.

All of this lands on an orphan `reach-data` branch (no shared history with
`main`, never merge it back) via `.github/workflows/reach.yml`, which runs on
a daily schedule and via `workflow_dispatch`. It is deliberately **not** part
of the CI gate — a stale GitHub token or a marketplace API hiccup must never
block a PR.

## The rules that keep the store honest

- **Never write a zero for a failed fetch.** Every source in `collect.mjs`
  runs inside its own try/catch. A source that throws — malformed payload,
  HTTP error, missing field — writes *nothing at all* for that run; it does
  not fall back to `0` or an empty object. `scripts/reach/sources.mjs`'s
  parsers exist entirely to enforce this: they throw on anything they can't
  positively confirm rather than defaulting a suspicious value to zero. The
  alternative — a parser that quietly returns `0` downloads because a field
  was missing — would write a permanent, indistinguishable-from-real cliff
  into months of history.
- **The merge rule is overwrite-and-keep.** For views and clones,
  `mergeDaily` in `scripts/reach/merge.mjs` overwrites every date the API
  returns and keeps every date it doesn't mention; it never deletes a date.
  That makes a run idempotent, makes today's still-accumulating count
  self-correcting (tomorrow's 14-day window includes today and replaces it
  with the final number), and means **a collector run at least once every two
  weeks loses nothing** — GitHub's window is 14 days, so a missed week
  backfills automatically the next time the workflow runs. Two missed weeks
  in a row is where a gap becomes permanent.
- **A corrupt store file fails loud, not silent.** `readJson` in
  `scripts/reach/store.mjs` distinguishes "file does not exist" (the normal
  first-run case, returns the caller's fallback) from "file exists but will
  not parse" (throws). If a run gets killed mid-write on a filesystem where
  `rename` isn't atomic, or a file is damaged some other way, the collector
  refuses to treat that file as empty — an operator who sees `collect.mjs`
  crash with a "corrupt JSON in …" error should **repair or delete the
  specific file it names**, not assume the store rebuilds itself, and
  certainly not let a run silently reinitialize it to `{}` (that would
  overwrite everything older than 14 days with nothing).
- **Downloads are not people.** Open VSX's `downloadCount` and the VS
  Marketplace's `downloadCount`/`install`/`updateCount` all count CI installs,
  version updates, and repeat installs by the same machine. They are a
  measure of traffic through the marketplace, not of distinct users. The
  rendered dashboard says this explicitly; don't strip that caveat out when
  editing `render.mjs`.

## What cannot be recovered

**Views and clones from before the first successful collection run are gone
permanently.** GitHub retains only the trailing 14 days for both endpoints
and destroys anything older — there is no API, paid tier, or export that
recovers it after the fact. For this repo specifically, the unrecoverable gap
runs from repo creation (2026-07-19) to whenever `reach-data` first receives
real numbers. No design in this collector closes that gap; the honest move is
to say so here and in the dashboard rather than imply the history is
complete.

## Tokens — resolved, and why there are two

Settled by live runs on 2026-08-22. Two tokens are in play because the
endpoints need opposite things:

| Endpoints | Needs | Token used |
| --- | --- | --- |
| `/traffic/views`, `/traffic/clones`, `/traffic/popular/*` | **push access** — a fine-grained PAT with `Administration: read` | `GH_TOKEN` (the `REACH_TOKEN` secret) |
| `/stargazers`, Open VSX, VS Marketplace | ordinary public read | `GH_PUBLIC_TOKEN` (Actions' built-in `github.token`) |

**The built-in `GITHUB_TOKEN` is not sufficient for traffic.** A dispatched run
returned `HTTP 403` on all four traffic endpoints while collecting stars and
marketplace data fine:

```
reach: ok=[stars, marketplace]
reach: FAILED views  — .../traffic/views  → HTTP 403
reach: FAILED clones — .../traffic/clones → HTTP 403
```

**And a fine-grained PAT scoped to `Administration: read` cannot read
`/stargazers`** — the mirror-image failure, observed on the very next run:

```
reach: ok=[views, clones, referrers, paths, marketplace]
reach: FAILED stars — .../stargazers → HTTP 403
```

Hence the split. Routing the public reads through the built-in token means the
PAT never needs a permission beyond `Administration: read` — the narrowest
grant that does the job, rather than widening the PAT until everything passes.

### Creating `REACH_TOKEN`

1. https://github.com/settings/personal-access-tokens/new
2. **Resource owner** `oznasi1`; **Repository access** → *Only select
   repositories* → `oznasi1/agent-flow`.
3. **Repository permissions → Administration: Read-only.** Nothing else is
   needed. (`Metadata: Read-only` is added automatically and is harmless.)
4. `gh secret set REACH_TOKEN --repo oznasi1/agent-flow`

A classic (non-fine-grained) PAT with `repo` scope also works, but grants far
more than this needs.

### Rotating `REACH_TOKEN`

Personal access tokens expire (or should be issued with an expiry). To
rotate:

1. Generate a new PAT with `repo` scope on the `oznasi1` account.
2. `gh secret set REACH_TOKEN --repo oznasi1/agent-flow` — this overwrites
   the existing secret; there is no separate delete step.
3. Trigger a manual run to confirm the new token works before the old one's
   expiry lands during an unattended scheduled run.
4. Revoke the old PAT once the manual run succeeds.

## Running the collector locally

The collector and renderer are both zero-dependency Node scripts —
`npm ci` is never required to run them.

```bash
GH_TOKEN=<a PAT with repo scope, or `gh auth token`> \
  node scripts/reach/collect.mjs --out /tmp/reach

node scripts/reach/render.mjs --data /tmp/reach --out /tmp/reach/index.html
open /tmp/reach/index.html   # or just open the file in a browser
```

`collect.mjs` exits non-zero if any source failed (check stderr for
`reach: FAILED <source> — <reason>`), but sources that succeeded are still
written — a partial failure is not a reason to discard the run. Point `--out`
at a scratch directory for local experiments; pointing it at a real
`.reach-data` checkout works the same way the workflow uses it, but be
careful not to commit scratch data to that branch by accident.

## Scheduling caveats

- GitHub disables scheduled (`on: schedule`) workflows automatically after
  **60 days with no repository activity** (pushes, merges, etc. all count).
  A quiet repo means the cron stops firing silently — there's no
  notification. `workflow_dispatch` still works to kick it back on, and
  doing so once resumes the schedule; if this repo goes quiet for two
  months, check that the workflow is still enabled before assuming the gap
  in `reach-data` is a bug.
- Because a single traffic fetch returns the trailing 14 days, the schedule
  in `reach.yml` (`17 6 * * *`, daily) has a lot of margin — even if a
  scheduled run is skipped or fails outright, the next successful run
  backfills the missed days automatically. The tighter risk is two
  consecutive misses spanning more than two weeks.
